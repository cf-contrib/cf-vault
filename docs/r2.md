# R2

R2 speaks the S3 API, so tools such as Terraform's S3 backend need an access key, a secret and a
session token. cf-vault delivers them as `CLOUDFLARE_R2_*` variables, from either of two places.

## From a broker

A broker profile with a `bucket` returns temporary credentials for it, limited to the key prefixes
the broker fills in. cf-vault delivers them with the API token, if the profile has one. See
[Broker](broker.md).

## Without a broker: an api_token profile

A `token` profile can derive temporary credentials from the stored API token:

```toml
[ci-state]
type = "api_token"
account_id = "abc123"

[ci-state.r2]
bucket = "org-terraform-state"          # exactly one; use one profile per bucket
permission = "object-read-write"        # or "object-read-only"
prefixes = ["github.com/example-org/app/"]
```

The token needs an R2 permission (Workers R2 Storage Write is known to work); without one,
Cloudflare answers with error `10000` and cf-vault says so. The credentials last **15 minutes**
unless `--ttl` is given, and **cannot be revoked early**: keep them short. A profile with no `r2`
table makes no R2 request.

`r2` is not valid on OAuth profiles: an OAuth session has no parent access key.

## What the command gets

| Variable | Value |
|---|---|
| `CLOUDFLARE_R2_ACCESS_KEY_ID`, `CLOUDFLARE_R2_SECRET_ACCESS_KEY`, `CLOUDFLARE_R2_SESSION_TOKEN` | the temporary credentials |
| `CLOUDFLARE_R2_ENDPOINT` | `https://<account id>.r2.cloudflarestorage.com` (or the broker's) |
| `CLOUDFLARE_R2_BUCKET` | the bucket |

cf-vault never sets or changes `AWS_*`. S3 tools read those, so map them for the one command that
needs them, or use a `credential_process` helper.

## Terraform's S3 backend

Point the backend at an AWS profile whose `credential_process` prints the credentials from
`CLOUDFLARE_R2_*`, such as
[`terraform-cloudflare-backend`](https://github.com/tf-contrib/terraform-cloudflare-backend), and run
Terraform under cf-vault:

```bash
cf-vault exec -p production --ttl 30m -- tofu plan
```

The helper does not pass the expiry on, so a run longer than the credentials' lifetime can fail to
save state: use `--ttl` for long applies.
